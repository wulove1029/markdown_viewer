## 2. 分階段執行

### P0：建立可比較的效能基線（估 1–2 工作日）

加入獨立 benchmark 與分段計時，記錄啟動、IPC、文件讀取、轉換、第一個可讀畫面、完整渲染、附屬面板完成時間。Markdown 需區分文字可讀與 Mermaid／數學式／圖片完成，不能只用 loadFinished 宣稱可讀。

測試組合：
- Markdown：10 KB、100 KB、1 MB、5 MB，包含長表格、程式碼、圖片、數學式與 Mermaid。
- PDF：10、100、750、3000 頁；分開文字型、掃描型、複雜向量與混合頁面尺寸。
- 文件庫：100、1000、10000 個支援文件，另含大量非支援檔案的目錄。
- 冷啟動、程式已啟動開檔、A→B→A 分頁切換、快速連續切檔、縮放、輸入與搜尋。

固定硬體、螢幕倍率、樣本、電源模式與打包版本。冷啟動明確記錄為程式重啟或系統重新開機，不混為同一組；暖開檔至少 30 次，啟動至少 10 次，記錄 p50、p95、最大 UI event gap、記憶體峰值。資料存入 docs/benchmarks，樣本使用合成資料，避免收錄私人文件。

交付：基線報表與依實際耗時排序的前三項瓶頸。

### P1：開檔速度（估 3–5 工作日，依 P0 排序調整）

1. 啟動與檔案總管開檔：驗證能否將 MainWindow 等重型匯入延到單一實例判斷後；IPC 改事件式收取，定義完整訊息邊界與重複開檔處理。延後非必要面板初始化；維持目前工作階段還原安全性。
2. 文件樹：背景掃描結果採差異更新、分批加入或展開時才建立子項，避免一次 clear + 全樹重建；保留選取、展開、捲動與標籤狀態。只有量測顯示需要才改 QAbstractItemModel，避免一次重寫檔案操作。
3. PDF：先取得可見頁所需尺寸，其餘分批補齊，或使用可失效的尺寸／大綱快取。混合尺寸文件需保持捲動錨點；遵守 QPdfDocument 執行緒歸屬，不能直接把既有 GUI 物件丟進 worker。
4. 同文件附屬資訊共用一次讀取結果；標籤內容未變更時避免寫回。附屬面板可延後顯示，但標註資料不得被尚未載入的空集合覆寫。
5. 熱門分頁快取採總記憶體預算與 LRU。先快取轉換結果、尺寸、大綱及閱讀位置；是否保留少量 viewer 由實測決定，不為每分頁無限制建立 WebEngine。

快取有效性至少含檔案路徑、mtime_ns、大小與必要的主題／渲染選項；外部變更、同路徑替換、重新載入、改名和刪除需正確失效。未儲存內容不能被磁碟快取取代；密碼不落磁碟。

### P2：操作順暢度（估 3–5 工作日）

- Markdown 預覽先量測整頁 setHtml 成本；低風險先做重複內容跳過、延伸既有過期結果防護以減少無效工作、依文件大小調整更新節流與滾動錨點。只有仍不達標才做穩定區塊增量更新，保留完整渲染退路。
- Mermaid／數學式／大型圖片採按內容需求處理；評估可見區域優先與結果快取。增量更新不得破壞 source-line 對應、表格編輯、註記定位或匯出內容。
- 延續既有 PDF 預覽與 tiles 管線，依新量測調整預取、精確重繪與排程，避免重做已完成的非同步化。
- 保留既有 generation／path 檢查，確保快速切檔時只讓最新請求更新畫面；量測無效工作與佇列累積，補齊可取消工作與排程上限。
- 讀檔時立即回應選取狀態；短載入不閃整頁提示，長載入顯示檔名與階段。若暫留舊畫面，明確標示正在切換並禁止誤編輯舊文件。
- 切換 MD／並排／Office 時保留游標、捲動、未儲存內容及最新快照，延續既有資料安全機制。

### P3：介面與操作體驗（估 3–5 工作日）

推薦方向：閱讀優先、工具按情境出現。保留現有左側文件庫與中央文件，右側大綱／標註依使用需求展開。

- 頂部保留開檔、搜尋、清楚的模式切換；格式工具集中在編輯狀態，進階功能放次層選單。
- 延伸 app/theme.py 統一間距、字級層次、圖示線條、圓角、分隔線、hover、焦點和 disabled 狀態；Qt 介面、Markdown 與 Office 色彩同步。
- 閱讀區提供舒適行寬、行距與留白設定；長表格和程式碼獨立橫向捲動，不擠壓全文。
- 分頁選取狀態更清楚，未儲存與編輯模式不只靠顏色辨識；保留同名檔案消歧，完整路徑可快速查看。
- 整合既有快速開啟與搜尋入口，明確區分檔名搜尋、全文搜尋和目前文件搜尋。
- 空白首頁提供開啟檔案、最近文件、繼續閱讀；載入失敗提供重試、檔案位置與可理解的原因。
- 驗證鍵盤操作、焦點可見性、亮暗模式及 Windows 100%／125%／150%／200% 縮放。

設計取向可選：A 閱讀優先（推薦，畫面安靜且保留完整功能）；B 工作台優先（工具常駐，操作入口更多但內容區較小）。先製作同一份文件的亮／暗靜態對照稿，確認視覺取向後再全面套用。本次未實際檢視執行中介面，以上屬設計提案，非視覺缺陷定論。

### P4：整合驗收與交付（估 2–3 工作日）

依變更執行既有相關測試，再跑完整回歸；以打包 EXE 重跑 P0 樣本並做真實顯示環境操作。提供前後效能表、亮暗畫面對照、已知限制與回退方式。發布另依專案既有流程處理。

## 3. 驗收目標（暫定，P0 後確認；不是已達成數字）

| 面向 | 建議目標 |
|---|---|
| 程式啟動到首份內容可讀 | 同機同樣本 p95 比基線降低至少 30%；列為挑戰目標 |
| 暖開本機 100 KB Markdown | 首個可讀畫面 p95 ≤ 300 ms，不含遠端圖片下載 |
| 已快取的乾淨分頁切換 | p95 ≤ 150 ms，閱讀位置不跳動 |
| 大型 PDF 開啟 | 同樣本首頁可讀 p95 降低至少 30%，分文字／掃描／向量報告 |
| 輸入／縮放／捲動 | 目標 60 Hz；主要操作 p95 幀時間 ≤ 16.7 ms，無超過 100 ms 的主執行緒阻塞 |
| 大文件庫 | 掃描及結果套用期間仍可打字、捲動及切檔；量測 UI event gap |
| 記憶體 | 明定共享快取上限；反覆開關 30 次後無持續成長趨勢 |
| 資料安全 | 未儲存內容、外部變更衝突、Office 快照、PDF 密碼及標註相關回歸全部通過 |
| 視覺與操作 | 各縮放比例無重要文字裁切；鍵盤可操作主要流程；亮暗模式狀態可辨識 |

網路／雲端路徑另列延遲組，不能承諾與本機 SSD 相同門檻。事件間隔只能衡量阻塞，不能取代真實幀時間與人工操作驗證。效能門檻以 benchmark 判定；一般 CI 以工作量、快取命中、取消與正確性測試防回歸，避免時間門檻造成不穩定測試。

## 4. 交付節奏與風險

總粗估 12–20 工作日，以單人開發和回歸時間計，非承諾工期；複雜增量 DOM 或虛擬文件樹另估。建議第一批先交 P0 + P1 的前兩個實測高收益項目，讓開檔改善可先驗收，再進 P2／P3。

主要風險：增量更新破壞註記位置、PDF 延遲尺寸造成閱讀跳動、快取增加記憶體或顯示過期內容，以及 UI 簡化使既有功能難找。對應以穩定區塊定位、錨點補償、嚴格失效與預算、保留快捷鍵和清楚次層入口降低風險。

不建議把整體框架遷移、大量動畫或單純升依賴版本當成本輪核心。是否調整依賴由可重現問題與相容性證據決定。
