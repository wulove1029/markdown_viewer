# Markdown Viewer 消費者體驗盤點

日期：2026-09-08。基準：本機 1.30.2，commit `96da981`。本次交付是盤點與改善順序，未修改產品功能。

## 判斷

目前功能已相當完整；更接近一般消費者的下一步，是讓「找文件、開始寫、整理搬移、確認有存好、匯出帶走」這幾條路徑更一致。先處理會令使用者以為資料不見、或需要改用滑鼠才能完成的問題，再降低首次使用的選擇成本。

本盤點以程式碼、隔離重現、既有測試與 Qt/WebEngine offscreen 截圖為依據；沒有真人可用性測試。下列使用者影響與優先序是產品判斷，不是已量測的使用者流失率或正式工期。

## 已有能力，應保留

- 已有首頁、最近文件、多分頁與回復工作階段。
- 已有閱讀／Markdown／並排預覽／Office 的文字模式選單、閱讀行寬與行距、亮暗主題、分開記憶 PDF 與文字縮放。
- 已有原子儲存、前一版備份、自動復原草稿、外部變更確認；問題是部分邊界流程與提示仍不完整。
- 已有文件庫、全文搜尋、快速開啟、標籤、反向連結、範本、圖片／附件、PDF 閱讀與多格式匯出。

依據：`README.md`、`CHANGELOG.md:5`、`app/window.py:937`、`app/recovery.py`、`app/atomic_io.py`。不建議把這些重新列成「新增功能」。

## 優先改善清單

P1＝優先修補可靠性與主要操作缺口；P2＝降低操作／理解成本。規模 S／M／L 為相對工程規模估計，需待設計確認，並非承諾工期。

| 順序 | 優先／規模 | 使用者會碰到什麼 | 建議結果 | 證據層級 |
|---|---|---|---|---|
| 1 | P1 / M | 新開分頁若未進入上次正常關閉的分頁清單，即使草稿還在，重啟流程也不主動發現 | 啟動時列出所有待復原草稿，直接繼續或另存；不只依賴舊分頁清單 | 隔離 session 邏輯重現；非真實殺程序測試 |
| 2 | P1 / M–L | 搬移筆記後附件相對連結失效；註記檔搬移失敗卻仍回報主檔成功 | 搬移前檢查依賴與衝突，更新連結或攜帶資源；部分失敗要明說並可回復 | 暫存檔案實跑 |
| 3 | P1 / M | 「所有文件庫內容」搜尋漏掉 `.markdown`、`.txt`；讀不到與零結果混在一起 | 搜尋範圍符合實際支援，顯示搜尋來源與略過原因；PDF 是否支援明確標示 | 副檔名漏搜已實跑；錯誤分類為程式確認 |

| 5 | P1 / S | 全域搜尋選中結果按 Enter 無反應，改用滑鼠才可開 | Down／Up／Enter 可完成從搜尋到跳轉的完整流程 | Qt 鍵盤／滑鼠事件實跑 |

| 7 | P2 / S–M | 首頁偏向開舊檔；首次新增前需先選資料夾、檔名、類型及編輯器 | 首頁可直接新增，把位置選擇整合為單一對話框並記住偏好 | 現況程式／畫面確認；改善屬設計建議 |
| 8 | P2 / S | Markdown／Office 名稱與三擊編輯需要先學；README 還指向隱藏按鈕 | 以用途補充名稱與就地編輯提示，更新操作文件，保留原快捷鍵與相容性保護 | 程式／文件確認；名稱偏好未做人測 |
| 9 | P1（長文客群）/ L | 大型 Markdown 首次轉換仍久等，舊量測不能代表真實首屏 | 先量打包版開檔到可閱讀，再做大檔模式、分段顯示與清楚的取消／切換回饋 | 既有量測＋現況程式，這次未重測延遲 |
| 10 | P2 / M | 匯出格式入口和完成回饋不同；更新下載期間不能操作主視窗 | 統一匯出入口與「開啟／顯示位置」回饋；長任務可取消或背景處理 | 匯出為程式確認；更新模態視窗已隔離實跑 |

### 1. 復原要讓使用者找得到

`app/session_state.py:166` 的重啟流程讀取 `open_tabs`，並以 `last_file` 作舊格式 fallback；它不列舉所有復原快照。隔離場景中建立一份有效草稿，但路徑不在舊清單且沒有 `last_file`，得到「有效草稿 1、恢復分頁 0」。這證明啟動發現路徑有缺口，**不代表草稿已刪除或所有崩潰都無法復原**。另外實跑了手動重開同路徑會使用的復原準備函式，以 stub 選擇復原，仍可取回草稿且不改動原檔；完整對話框操作未在此情境重演。

建議啟動時列出可恢復項目，顯示文件名、時間與可預覽內容；儲存狀態也應區分「已寫入原檔」「已保留復原草稿」「尚未儲存」。目前已存檔訊息為短暫狀態列提示（`app/window.py:3695`），不宜把復原草稿稱為原檔已自動儲存。

驗收：開新分頁→編輯→等待草稿落盤→異常結束→重新開啟，不必自己找路徑就看得到待復原內容；重開／捨棄均需尊重現有保護。真正終止程序的完整場景仍待實作後測試。

### 2. 搬移應保護整份筆記的關聯資料

暫存重現中，筆記的 `assets/attachment.txt` 在搬移前可解析、搬移後不可解析，資源仍留在原資料夾。另在目的地已有註記檔的衝突場景，主檔成功改名／搬移，舊註記留在原處，函式仍回成功 mapping。見 `app/file_ops.py:100` 的文件搬移與 `:105` 的 sidecar 迴圈，以及可靠性分報告。

建議不是直接搬走整個共用 assets 資料夾，而是先辨識引用關係，選擇重寫相對路徑或複製必要資源；對共用資源避免破壞其他文件。主檔、註記與索引變更需預檢並處理部分失敗。

驗收：跨資料夾搬移後圖片、附件與標註仍可用；目的註記衝突／資源唯讀時，使用者看到具體失敗項目，原資料可回復。這也應是日後「打包分享含附件」功能的前置基礎。

### 3–5. 搜尋與快速開啟要形成完整路徑

- `app/global_search.py:99` 只收 `.md`，但 `app/file_types.py:7` 支援更多類型；同字測試確實略過 `.markdown` 與 `.txt`。先補文字類型與現有編碼讀取器，再決定 PDF 索引策略，不把 PDF 全文搜尋當作已存在。
- `app/window.py:5178` 的 Ctrl+P 候選只有最近文件與目前文件同層；深層文件與尚未開過的文件庫內容不保證能找。應重用背景掃描結果，避免每次 Ctrl+P 同步掃磁碟。
- `app/quick_open.py:102` 只顯示檔名；不同路徑的 `Meeting.md` 在清單中相同。建議直接顯示文件庫／相對路徑。
- `app/global_search.py:204` 的結果清單只連接滑鼠點擊；Qt 實跑 Return 開啟 callback 為 0，滑鼠點擊為 1。`:216` 雖然處理搜尋輸入框 Enter，但不是結果清單啟動。補 Enter 及焦點路徑是小改動但高頻受益。
- `app/global_search.py:73`、`:106`、`:301` 將略過檔案與空結果聚成同一結果。應區分「沒有來源」「來源離線／無權限」「有搜但沒有匹配」，提供對應下一步。

驗收：文件庫中從未開過的文字檔可用檔名／內容找到；同名檔無需滑鼠辨識；Ctrl+Shift+F→輸入→Down→Enter 可跳到正確結果；略過數與原因可檢視。

### 6. 小視窗設定頁

`app/settings_dialog.py:117` 將各頁直接放入 QTabWidget，沒有外層可捲動內容。獨立 probe 載入 Windows 中文字型後，要求 800×540，實際視窗被限制為 800×757；按鈕列底端 745，QScrollArea 數量 0。

1920×1080 在 150% 縮放下約為 1280×720 邏輯空間，還需扣除工作列／標題列，因此有超出可用高度的風險。這是幾何推論，**不是已在實體 150% 顯示器上證實裁切**。

驗收：在可用高度 540–720 的視窗中，所有設定與底部動作皆可達；實體 Windows 125%／150%／200% 分別確認字體、下拉選單、焦點與捲動。

### 7–8. 開始寫與理解介面

首頁已可拖曳、開檔、查看最近文件（本次點擊已驗），但沒有新增入口（`app/renderer.py:457`）。第一次新增又可能先開資料夾選擇，接著才開新增對話框（`app/window.py:4749`、`app/new_note_dialog.py:77`）。優先將「新增筆記」放首頁，整合位置選擇；「先寫再命名」牽涉未命名草稿生命週期，應另行設計，不能只略過存檔對話框。

模式可以補充「文字編輯」「編輯＋預覽」「視覺編輯」的用途說明；保留含特殊語法文件進入 Office 的相容性提醒。閱讀模式的三擊編輯可增加右鍵／滑鼠提示，使功能不依賴隱藏手勢。

README 仍說點鉛筆、layers 按鈕與 Tools→偏好設定（`README.md:57`、`:59`、`:154`），但按鈕已隱藏，由模式選單取代（`app/window.py:1002`），設定入口位於「設定」（`:778`）。先同步使用說明，是最便宜的便利性改善之一。

### 9. 效能以真正可閱讀時間作目標

前次 2026-09-07 的合成元件量測：1 MB Markdown 冷轉換 p50 約 2.26 秒、5 MB 約 20.09 秒（`docs/benchmarks/upgrade-after.json:111`、`:156`）。這些數字不含 WebEngine 首屏，也不是本次重新量測。`app/renderer.py:465` 已有載入提示，不能說完全沒有回饋。

建議先量「檔案總管雙擊→視窗出現→文件可閱讀」，覆蓋一般文字、表格／圖表長文、掃描 PDF、複雜向量 PDF與 USB 文件庫，再按瓶頸決定分段載入／大檔純文字模式。PDF 與樹狀清單已有排程／快取，不宜直接重寫所有效能架構。

驗收目標應於建立基線後訂定：至少需記錄 p50／p95、載入中能否切換文件、取消舊任務是否仍阻塞新任務。不要以 `import main` 耗時取代真正冷啟動，也不要把 offscreen smoke 當實際 FPS。

### 10. 匯出和更新的回饋一致

PDF 完成後提供「開啟 PDF」按鈕（`app/export_actions.py:494`）；Word／PPT 只給五秒狀態列訊息（`:152`、`:208`）；HTML 只允許 Office／WYSIWYG（`:213`）。建議一個清楚的匯出入口，列出格式、必要限制與「開啟檔案／顯示資料夾」的相同完成回饋。PDF 目前有完成按鈕，並非自動開啟。

PDF 進度是不可取消的 ApplicationModal（`:466`）；Word／PPT 由事件處理函式呼叫轉換（`:135`、`:191`），長文是否卡住需另外量測。更新下載也已隔離確認為模態、無取消、不定進度；未連網下載或安裝更新。本次不宣稱所有格式匯出慢或更新失敗。

## 建議排程

另有三項可納入第二批的便利性改善（詳見可靠性分報告 R4／R5／R7）：

- **外部衝突可比較、另存副本**：目前已有覆寫／捨棄確認，但保留雙方版本的入口不足。補上 Markdown／TXT 另存新檔，對唯讀檔與同步衝突也有幫助（`app/window.py:3652`、`:5465`）。
- **儲存狀態與上一版可見**：保留現有 `.bak` 與草稿機制，加上持續狀態、失敗後的重試入口，以及查看上一版。避免使用者誤把草稿備援當成原檔已存（`app/window.py:3359`、`:3695`、`app/atomic_io.py:92`）。
- **安裝過程更貼近繁體中文用戶**：目前安裝腳本要求 admin、僅設定英文語系；可規劃每位使用者安裝／可攜版、繁中精靈與檔案關聯選項。這是來源檢查，未執行安裝或驗證 Windows 預設程式行為（`installer.iss:23`、`:27`、`:43`）。

1. **先把資料與主要操作補齊**：復原發現、搬移附件／註記、搜尋副檔名與 Enter、小螢幕設定。若主要客群是長文閱讀者，同批建立冷啟動／大檔基線。
2. **再減少日常步驟**：Ctrl+P 文件庫範圍與同名路徑、首頁新增、搜尋失敗可行動提示、文件與名稱一致。
3. **再投入較大優化**：大型文件漸進呈現、匯出／下載背景任務、需要時做含附件的分享套件。

每一批以可觀察的使用者流程驗收，不以「多了幾個按鈕」驗收。此階段沒有足夠證據支持先擴增更多 AI、圖表或雲端功能。
